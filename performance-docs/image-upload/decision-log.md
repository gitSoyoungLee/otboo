# 이미지 업로드 부하 실험 – 결정 기록

> 자기소개서 재료 문서 9장("본인이 직접 내린 결정")의 원본.
> 본인 표현은 그대로 옮기고, Claude가 제안한 근거는 따로 구분해 적는다.

## 2026-11-24 · 2단계 [결정] 힙 크기와 동시 사용자 단계

- **결정:** 힙 `-Xmx384m`, 동시 업로드 사용자 1 → 2 → 4 → 8 → 16 → 32 (2배씩)
- **본인 발언(원문):** "이미지 실험 네가 추천하는 안대로 하고, 선택 이유도 네가 적절히 적어줘."
- **채택한 근거 (Claude 제안, 본인 채택. 본인 표현 아님):**
  1. 384m는 팀이 Docker 배포 설정(`.env.docker`의 `JVM_OPTS="-Xmx384m -Xms256m"`)에 실제로 쓴 값이라, "운영 서버의 한정된 메모리"를 재현한다고 말할 근거가 있다.
  2. 1단계 계산상 4000×3000 이미지 1장을 디코딩하는 데 약 34~46MiB가 필요하다(추정치). 384m에서는 한 자릿수 동시 요청에서 문제가 생길 수 있으므로, 그 근처를 촘촘히 보기 위해 2배씩 늘린다.
  3. 2배씩 늘리면 HikariCP 기본 풀 크기(10)를 넘는 구간(8 → 16)도 지나가서, 메모리 병목과 커넥션 고갈을 구분해서 관찰할 수 있다.
- **고려했지만 고르지 않은 선택지:** 512m / 1g 힙, 10→30→50→100, 5→10→20→30
- **측정 계획:** 단계마다 워밍업 1분 + 유지 3분, 3회 반복해 평균과 p95를 기록한다.
- **주의:** 자기소개서에 "직접 내린 결정"으로 쓸 때는 위 근거를 본인이 이해하고 본인 말로 설명할 수 있어야 한다. 6단계 면접 질문에서 "왜 384m, 왜 2배씩?"을 점검한다.
