# 비밀번호 초기화 리팩토링 – 결정 기록

> 자기소개서 재료 문서 8장("본인이 직접 내린 결정")의 원본. 본인 표현을 그대로 옮긴다.

## 2026-11-24 · 1단계 보고 후 방향 결정 (본인)

1. 4단계 주제는 네 제안대로 "공유 풀(eventExecutor) 포화 → 비밀번호 초기화 요청 실패와 알림 등 다른 기능으로의 장애 전파"로 바꾼다.
   메일 서버를 느리게 만든 상태에서, 개선 전후로 알림 처리 지연과 초기화 요청 실패율을 측정해 줘.
2. 3단계(장애 2)를 이번 작업의 핵심으로 둔다. "메일 실패 시 계정 잠김"과 "인증 없이 타인 비밀번호 무효화" 두 가지를
   각각 실패하는 테스트로 재현해 줘. [결정]에서는 비밀번호 초기화 방식 자체를 바꾸는 선택지(기존 비밀번호 유지,
   재설정 링크 방식 등)와 요청 횟수 제한을 함께 비교해서 보여줘.
3. 메일 실패 시 원인이 로그에 안 찍히는 문제도 3단계에서 함께 고친다.
4. 2단계에서 AFTER_COMMIT으로 바꾸면 4단계에서 풀이 꽉 찼을 때 동작이 달라질 테니, 그 영향도 4단계에서 설명해 줘.
5. eventExecutor 설정은 내가 만든 게 아닐 수 있어. git blame으로 누가 언제 추가했는지 확인해서 문서의 "배경"에 적어 줘.
   자기소개서 재료 문서에서는 내가 한 것과 팀원이 한 것을 반드시 구분해 줘.

## 2026-11-24 · 3단계 [결정] 장애 2 대응 방식 (본인)

- **선택:** A + C
  - A. 기존 비밀번호 유지 + 임시 비밀번호 병행 (임시 비밀번호를 별도 컬럼에 저장, 로그인 시 둘 중 하나 일치하면 성공)
  - C. 요청 횟수 제한 (이메일·IP 기준)
- **본인 발언(원문):** "A + C"
- **이유:** 본인이 따로 말하지 않음(미기재). 자기소개서에 쓰기 전에 본인 말로 이유를 정리해야 한다.
  - 참고로 Claude가 제안할 때 든 근거(본인 표현 아님): A만으로 실패 중인 2-1·2-3 테스트와 10분 만료 잠김이 해결되고, 프론트 소스가 저장소에 없어 화면 변경이 필요 없는 방식이 끝까지 증명 가능하다. C는 A로 못 막는 메일 폭탄·남용을 보완한다.
- **고르지 않은 선택지:** B. 재설정 링크(1회용 토큰) 방식 → 면접 "실제 운영이라면?" 답변 재료로 남김
- **보류:** 이메일 존재 여부와 무관하게 항상 204 응답(계정 존재 노출 방지). 이번 결정에 포함하지 않음.
